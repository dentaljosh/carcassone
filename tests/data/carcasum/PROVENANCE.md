# Vendored Carcasum reference data — provenance

Reference tile data for a **second, independent** differential tile oracle
(`tests/test_carcasum_tile_oracle.py`), mirroring
`tests/test_jcz_tile_oracle.py` / `tests/data/jcz/`. Nothing here is engine
code; it certifies `engine/wingedsheep/carcassonne/tile_sets/base_deck.py`
against a *second* open-source Carcassonne implementation, independent of the
JCloisterZone lineage the first oracle uses.

Despite living under a `jcz/` directory in the Carcasum tree (Carcasum's tile
data format and half-edge convention were themselves derived from an older
JCloisterZone build), this is a **distinct 2014-vintage pack**, not a copy of
the `tests/data/jcz/jcz_basic_5x.xml` (JCZ 5.x) reference the first oracle
uses — different project, different commit history, different tile-kind
count. The two oracles are independent by construction.

### Two structural facts a reader must know

1. **The garden-variant collapse.** Carcasum's 2014 `basic.xml` has **only 24
   tile kinds** (no `<garden>` tag exists anywhere in the file) where our deck
   and JCZ 5.x both carry **32** (24 base + 8 "flowers" graphic variants as
   distinct ids). Carcasum simply folds each garden variant's copies back into
   its non-garden sibling's `count` — e.g. Carcasum's `Ccc` has `count="3"`,
   which is our `city_bottom_grass` (2) + `city_bottom_grass_flowers` (1). So
   the pairing in `TILE_MAPPING.tsv` is a **total, many-to-one function**
   (OUR kind → Carcasum id), not the 1:1 pairing the JCZ table has — visible
   directly in the TSV as repeated `carcasum_id` values. The **deck-count
   multiset still agrees exactly**: 24 kinds/72 tiles on their side, 32
   kinds/72 tiles on ours, and every Carcasum id's count equals the sum of the
   our-kinds mapped to it (verified in the oracle test).

2. **The R9 recurrence.** Exactly one Carcasum kind disagrees with our
   (R9-flag-off) data, and it is the **same kind, the same divergence**
   already named R9 in `tests/data/jcz/PROVENANCE.md` /
   `engine/.../tile_sets/base_deck.py`: `city_top_straight_road` (Carcasum
   `RCr`, ×4) declares its north (city) field region as `EL WR` only —
   `<farm city="N">EL WR</farm>`, byte-identical text to JCZ 5.x's
   equivalent declaration. Our engine (flag off) additionally claims `NL NR`
   (our `TLT`/`TRT`) in that region, which lie on the tile's own north CITY
   edge. This is **not a second, independent finding** — it is the *same*
   remediation (`CARCASSONNE_FIX_R9`) reproducing verbatim against a wholly
   separate upstream codebase, which is a stronger corroboration of R9 than
   either oracle alone: two unrelated implementations, ten years apart,
   agree with each other and disagree with us in the identical, exact way.
   With `CARCASSONNE_FIX_R9=1`, all 32 of our kinds agree with Carcasum
   field-for-field — zero divergences.

## `TILE_MAPPING.tsv`

Generated by `measurement/carcasum_tile_diff_20260823/carcasum_tile_diff.py`
on 2026-08-23 and checked in as the **pinned expectation** for the 32-row
pairing (our kind ↔ Carcasum id ↔ Carcasum `tileType` ↔ deck count ↔ resolved
rotation). The oracle re-derives the pairing from scratch every run and
asserts it equals this table, so a silent re-pairing cannot mask a
field-data divergence. Columns:

| column | meaning |
|---|---|
| `our_kind` | key into `base_deck.base_tiles` |
| `carcasum_id` | the `id` attribute of the matching `<tile>` in `carcasum_basic_2014.xml` |
| `carcasum_tile_type` | Carcasum's engine-internal `Tile::tileType` for that id — the **0-based index of the `<tile>` element in XML declaration order** (see "tileType numbering" below); load-bearing for anything that would force a specific tile via `Game::getTileIndexByType` |
| `deck_count` | our count for `our_kind` (NOT the Carcasum id's count, which can be the sum over several rows — see the garden collapse above) |
| `rot_cw90` | number of 90°-clockwise rotations applied to OUR tile's base orientation to align with Carcasum's declared orientation |
| `edges_NESW` | Carcasum's edge terrain string (C=city, R=road, F=field), N/E/S/W order |
| `carcasum_fields` / `our_fields` | the farm/field regions each side declares, in the shared half-edge notation (see below), post-rotation |
| `verdict` | `MATCH` (field-for-field identical) or `FIELD_DIFF` (the R9 case, the only one) |

### tileType numbering (confirmed from source, not inferred)

`jcz::TileFactory::readXMLTile` (`Carcasum/jcz/tilefactory.cpp`) assigns
`TileTypeType type = (TileTypeType)tileTemplates[set].size();` **before**
appending the newly-read tile to `tileTemplates[set]` — i.e. `type` is the
0-based count of tiles already read for this set, which for a file read
top-to-bottom is exactly the tile's declaration order in the XML. This value
is then passed through `Util::toGlobalType(Tile::BaseGame, type) == type + 0`
(a no-op for the single-expansion base game), so **global tileType ==
declaration-order index**, 0..23:

```
0 L        4 CccR+     8 Cc.1     12 Ccc      16 RrC      20 RRRR
1 LR       5 CccR      9 Cc+      13 Ccc+     17 C        21 RRR
2 RCr      6 CFc+     10 CcRr     14 CRr      18 CFC.2    22 Rr
3 Cccc+    7 CFc.1    11 CcRr+    15 CRRR     19 CC.2     23 RFr
```

### Start tile: confirmed `RCr` = our `city_top_straight_road`

`RCr` is the only `<tile>` carrying a `<position x="0" y="0"/>` element.
`TileFactory::createPack` special-cases exactly this: the **first** clone of
a tile with `data.hasPosition` is `pack.prepend()`-ed (every other clone,
including that same tile's remaining count, is `pack.append()`-ed in normal
declaration order); `Game::newGame` then does
`board->setStartTile(tiles.takeFirst())` — i.e. takes the prepended tile.
Since only one `<tile>` in the whole pack has a `<position>`, this
unambiguously makes `RCr` (tileType 2) the fixed start tile, i.e. our
`city_top_straight_road`.

### `Game::getTileIndexByType` grouping assumption: HOLDS

`Game::getTileIndexByType` (`core/game.h`) assumes `tiles` (the vector built
by `createPack`, *after* `takeFirst()` removes the start tile) is grouped by
ascending `tileType` in contiguous runs, and does a `tileCount[i]`
prefix-sum to find where type `tileType`'s run starts. Traced by hand: for
each type `t` in declaration order 0..23, `createPack` appends `count[t]-1`
clones (or all `count[t]` when `t` has no position) to the growing end of the
list, and prepends only ever fires once (for `RCr`'s very first clone, at
`t=2`). So the pack, before `takeFirst()`, is
`[RCr] + [type0 x4][type1 x2][type2 x3][type3 x1]...[type23 x8]` — one
contiguous ascending-`tileType` run per type, with the special-cased tile
stuck on the front. `takeFirst()` removes exactly that one prepended
element and nothing else, so the remainder is **still** grouped ascending by
`tileType`, contiguous, just with `RCr`'s own run shortened by one (3
instead of 4) — and `tileCount[2]` is built by literally counting the
remaining tiles, so it correctly reads 3. **The grouping assumption holds**;
`getTileIndexByType` (and therefore forcing a specific `tileType` via
`Game::getTileByType`) works correctly on this pack, including for the
prepended tile's own type. (Had a second tile ever declared a `<position>`,
or the loop order differed, this could break — but only `RCr` does.)

## Where this came from

Built 2026-08-23 to mirror `tests/data/jcz/` against a second, independent
open-source implementation. Generator:
`measurement/carcasum_tile_diff_20260823/carcasum_tile_diff.py` — adapted
from `measurement/jcz_spike_20260803/jcz_tile_diff.py` (imports its
`TileModel` / half-edge tables / `parse_ours()` unchanged; adds a new
`parse_carcasum()` for Carcasum's XML schema and a new `match_collapsing()`
matcher for the many-to-one pairing, since the original `match()` assumes a
1:1, count-equal pairing that doesn't hold here — see the module docstring
for the itemized adaptation).
