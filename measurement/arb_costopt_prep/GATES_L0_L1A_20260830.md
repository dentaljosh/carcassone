#### The R9 constraint and the choice made

`tier1::with_legacy_scorer` sets a **thread-local** flag, and it does NOT
propagate into `tiearb::arbitrate_core`'s `std::thread::scope` workers
(`tier1.rs` ~:236 / `tiearb.rs` ~:644). An identity gate written as
`with_legacy_scorer(|| arbitrate(.., threads=4))` would therefore run the FLAT
scorer in every worker and compare **flat against flat** — green, and worthless.
Two ways out: (1) propagate the TLS into the scoped workers for the legacy leg,
or (2) run the LEGACY leg single-threaded and the FLAT leg threaded.

**This gate takes (2)**, for three reasons, recorded because the choice is the
gate's validity:

1. **No production-code change.** Option (1) means teaching `arbitrate_core`
   about a gates-only flag — new code on the deployed path, written to test the
   deployed path, whose own correctness then stands between the gate and the
   truth.
2. **It is the strictly stronger contrast.** `arbitrate` is thread-count
   invariant *by design* (order-preserving fold; `threading_is_bit_identical_to_sequential`),
   so `legacy@t=1` is a fixed, thread-free reference. Grading
   `flat@t ∈ {1,2,4,8}` against it closes both questions in one assertion —
   "is the flat scorer the legacy scorer" AND "do the flat scorer's
   thread-local `Decomp`/`Scratch` buffers leak across workers". Option (1)
   would have compared `legacy@8` to `flat@8`, which tests the buffers only
   against a reference that has no buffers to leak, and adds a TLS-propagation
   mechanism that could itself paper over a leak.
3. **The failure it exists to catch is thread-count dependent** (a shared-buffer
   race), so a green `t=8` against a `t=1` reference is exactly the receipt owed.

`border_fallbacks == 0` over the whole gate ⇒ every compared value came from
the flat route, not from the legacy fallback.

**Bug found and fixed while landing it (worth its own line).** `BORDER_FALLBACKS`
is a **process-wide** atomic, so any two tests that read it as a *scoped* count
race under `cargo test`'s parallel runner: the new gate passed solo and FAILED
in-suite because `tier1`'s border test had bumped the counter. Both pre-existing
readers had the same latent race (one is `#[ignore]`d, which is why it never
fired). Fixed with `tier1::BORDER_FALLBACK_GATE`, a `#[cfg(test)]` mutex all
three now hold.

## 2. L1a — the meeple-phase decomposition hoist

### What changed

`search::Searcher::evaluate`: when the expanding node is in `Phase::Meeples`,
every child reuses the **parent's** `Decomp` instead of running its own
`leaf::decompose_into`. Call-site logic only — **`decompose_into`'s interface is
untouched**, so the concurrent L1 delta-decompose spike composes with it.

`Decomp` gained `#[derive(PartialEq, Eq)]` (every field is an integer or bool
vector, so structural equality *is* bit-identity) — additive, for the gates.

**Why it is bit-identical by construction, not by measurement.**
`decompose_into` is a pure function of the TILE BOARD: it reads
`state.placed_coords` and `state.board`, and no meeple / score / phase / deck
field appears anywhere in its body. A node in `Phase::Meeples` has only
`Action::Meeple` and `Action::Pass` legal, and `GameState::apply_action` routes
both to code that never places a tile. So the child's decomposition IS the
parent's. The gates below are the falsifier, not the argument.

No knob, no config field, **no strength claim owed** — the tier1-swap /
threads-arming precedent.

The four routes in the end-to-end gate are exactly the four the hoist's validity
argument has to cover — in particular `use_leaf_scratch = false`, the one route
where `leaf_at` never populates the scratch and the hoist must decompose the
parent explicitly, and `dose ≠ 0`, where the hoisted decomposition also feeds
`jrules_prior_term`.

`with_fresh_decomp` is a `#[doc(hidden)]`, gates-only thread-local exactly like
`tier1::with_legacy_scorer` — nothing in production calls it; it exists so the
identity gate can run both routes without re-implementing the search.

### Realized factor — **1.031× pooled, BELOW the sweep's 1.06–1.07×[M]**

`cargo test -p carc-core --release -- --ignored --nocapture bench_meeple_hoist`,
1376 sims, 8 **interleaved** A/B reps per root:

| root | fresh | hoist | factor |
|---|---|---|---|
| `28000000000` ply 30 | 152.01 ms | 143.91 ms | **1.0563×** |
| `28000000000` ply 55 | 182.42 ms | 171.49 ms | **1.0638×** |
| `42` ply 80 | 337.21 ms | 328.31 ms | 1.0271× |
| `11` ply 105 | 564.87 ms | 555.67 ms | 1.0165× |
| **POOLED** | 309.13 ms | 299.85 ms | **1.0309×** |

Two honest caveats, in both directions:

* **Shared box.** Contention adds a roughly common additive term to both legs,
  which pulls a paired ratio TOWARD 1. The exclusive factor is very likely
  higher than 1.031×. (Note this is the opposite sign to §3b's inflation, where
  the two legs have very different allocation profiles; here both legs run the
  same code but for one `decompose_into` per child.)
* **It decays with ply** — 1.056 / 1.064 / 1.027 / 1.017 across plies
  30/55/80/105, monotone in ply on this sample. The early-game reads bracket
  the sweep's 1.06–1.07×; the late-game reads are half of it. A single-root,
  early-ply measurement would have reproduced the sweep and been misleading:
  a production s/move average weights late plies heavily.

**Owed:** an exclusive-box re-read of this table before L1a's factor enters the
Cheap-3 arithmetic (`1.11× arb-off / 1.70× arb-on / 2.20× deploy`). On this
evidence the search-path contribution should be carried as **~1.03–1.06×,
ply-dependent**, not a flat 1.06–1.07×.

### Scope NOT taken: the tier1 / arbiter consumer

The sweep priced L1a at "1.06–1.07× on EVERY consumer". Only the **search** path
is hoisted here. `tier1::best_by_virtual_score` has the same opportunity — in a
meeple-phase decision no candidate places a tile, so both the per-candidate

siblings and equal to the parent's — and it is the consumer the arb-on 1.70×
rests on.

exact function `G-BITEXACT` grades, and any edit there owes a re-run of §2
